Reprise et fiabilisation de code existant

Ma définition Mes éléments de preuve Mon autocritique Mon évolution Réalisations liées

Ma définition

La reprise d'un code existant consiste à comprendre l'état de développement dans lequel il est, en analysant les choix techniques réalisés et le fonctionnement des fonctionnalités, et ce qu'il reste à finir, tout ça avant de pouvoir procéder à son évolution ou à sa fiabilisation. La fiabilisation quant à elle consiste à s'assurer lors du développement que les choix techniques réalisés ne créeront pas de dette technique par la suite.

Cette compétence est différente de partir de zéro : elle demande une partie de rétro-ingénierie (analyser le fonctionnement d'une chose déjà mise en place en la détaillant partie par partie) pour comprendre un existant et ne pas casser de fonctionnalité en la modifiant.

Lors de la fiabilisation du code, une des questions qui se pose est quel choix technique faire en fonction des délais demandés, c'est là que la dette technique peut arriver. La dette technique représente le temps qui sera consacré après la mise en production pour régler des problèmes qui auraient pu être évités si plus de temps avait été consacré au développement.

La dette technique peut amener des coûts supplémentaires dans les services informatiques, comme nous le dit cet article du Journal du Net, qui nous apprend que 20 % à 30 % du budget total est consacré à la maintenance. Ces surcoûts sont dus à la maintenance évolutive et corrective que crée la dette technique ; les professionnels interrogés estiment à 60 % que la dette technique est souvent à l'origine d'incidents qui ralentissent les développements.

Mes éléments de preuve

La reprise d'un code existant et de sa fiabilisation est une compétence qui ne peut s'obtenir qu'en travaillant sur des projets déjà existants. Pour la fiabilisation de code il y a l'expérience mais aussi les manières de travailler qui comptent, mes cours m'ont permis de comprendre comment bien faire du code. Les projets sur lesquels j'ai travaillé m'ont permis après analyse de leur code de comprendre la manière de travailler de mon entreprise et des développeurs ayant travaillé sur les projets.

Ici je vous parlerai de quelques projets sur lesquels j'ai dû mobiliser cette compétence :

Lors de la reprise du code de l'application de suivi de commandes Gedim, j'ai dû y rajouter des fonctionnalités. Une de ces fonctionnalités avait été en partie développée, mais était incomplète : cette fonctionnalité était la page d'administration des utilisateurs. J'ai dû rattacher cette page pour qu'elle soit visible, puis ajouter des options supplémentaires afin de pouvoir ajouter et gérer les utilisateurs avec toutes leurs caractéristiques. Cette fonctionnalité n'est pas très utilisée car la base d'utilisateurs (environ 50) ne bouge pas beaucoup, mais elle était nécessaire pour éviter de modifier manuellement les utilisateurs.

Un autre code que j'ai dû reprendre est celui de l'intégration de l'API Géodis, qui avait été inachevée et demandait une reprise de son code. J'ai donc dû voir où le développement s'était arrêté et si les fonctionnalités étaient toujours opérationnelles. J'ai également pu reprendre les échanges par mail avec les équipes techniques de Géodis, ce qui m'a permis de faire évoluer le projet de façon beaucoup plus efficace. Ce projet étant toujours en cours et en phase de tests, il n'y a pas de résultats à annoncer, mais ces tests sont réalisés et les problèmes rencontrés sont réglés au fur et à mesure.

Mon autocritique

Cette compétence je n'ai pu l'exercer que dans deux projets mais cela m'a permis de comprendre les enjeux de la reprise de code et de comment il était possible de bien le fiabiliser.

Actuellement je ne peux pas me considérer comme un expert dans ce domaine à cause du peu de projets que j'ai pu reprendre, mais j'ai confiance en ma capacité de fiabiliser du code grâce à l'expérience que j'ai obtenue sur les projets sur lesquels j'ai pu développer. La partie reprise de code et/ou du projet qui va avec est parfois plus difficile, car elle demande une compréhension de toutes les fonctionnalités implémentées. Il me reste donc à développer la compétence de reprise de code, car je n'ai repris que du code API et web.

La compétence de reprise et fiabilisation est primordiale pour les experts ingénieurs logiciel afin de limiter l'accumulation de dette technique et ainsi permettre la pérennité des systèmes informatiques.

J'ai progressé dans cette compétence au rythme des projets sur lesquels j'ai travaillé car l'expérience obtenue m'a permis de me rendre compte qu'un code bien réalisé est plus facile à reprendre. Cette compétence s'exerce pleinement dans mon travail car en travaillant sur des projets d'évolution de code et de reprise j'ai pu apprendre la manière avec laquelle il était possible de reprendre du code et ce qui permettait d'en faire un code facilement fiabilisable.

Si je devais donner un conseil à un développeur qui commence dans ce domaine je lui dirais que c'est une compétence difficile à obtenir mais qu'une fois maîtrisée elle permet d'élargir le champ de compétence de façon considérable.

Mon évolution

Afin d'atteindre mon objectif personnel, qui est de créer mon API de domotique, je devrais trouver des projets similaires pour analyser leur fonctionnement.

Je pourrais également, afin de me diversifier dans les types de code repris, regarder ce qu'il est possible de faire en domotique en dehors des API, par exemple le fonctionnement d'un Home Assistant (serveur central dans un système de domotique permettant le contrôle et le paramétrage des appareils).
